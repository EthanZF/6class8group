# 第 2 章 软件质量分析方法及工具

> 本章说明本次质量分析"看哪些质量要素、用什么方法看、用什么工具看"。
> 分析对象为 `EthanZF/6class8group` 仓库 `main` 分支（commit `b011a5a`），源码位于 `src/` 目录。
> 本章所有数字均为实际运行工具所得，运行环境：macOS / Python 3.11.9 / Django 5.2.17。

## 2.1 分析的软件质量要素

软件质量分为**内部质量**与**外部质量**两类。内部质量关注"代码本身写得好不好"，用户看不见，但决定了后续维护成本；外部质量关注"程序跑起来对不对、稳不稳"，用户能直接感知。本次分析同时覆盖两类，但侧重内部质量——因为这是泛读阶段能够在**不启动完整运行环境**的前提下系统开展的部分。

### 2.1.1 质量要素与分析维度对照

| 质量类别 | 质量要素 | 具体观测点 | 本次是否分析 |
|---|---|---|---|
| **内部质量** | 可读性 | 注释覆盖率、命名规范、代码格式一致性 | ✅ 重点 |
| | 可维护性 | 圈复杂度、函数长度、可维护性指数（MI）、重复代码 | ✅ 重点 |
| | 可测试性 | 测试用例数量、测试代码占比、测试覆盖的模块 | ✅ 分析 |
| | 安全性 | 硬编码凭据、SQL 注入、命令注入、弱加密 | ✅ 分析 |
| | 规范性 | PEP 8 符合度、导入规范、异常处理规范 | ✅ 重点 |
| | 设计质量 | 模块化、信息隐藏、高内聚低耦合、抽象层次 | ✅ 人工分析 |
| **外部质量** | 功能正确性 | 单元测试通过率 | ✅ 有限分析（依赖环境） |
| | 缺陷密度 | 静态工具报告的问题数量与严重度 | ✅ 分析 |
| | 性能 | N+1 查询、缓存策略、索引设计 | ✅ 分析 |
| | 可靠性 | 异常处理完整性、并发安全 | ✅ 分析 |
| | 易用性 | 界面一致性、交互流程 | ❌ 由第 1、3 章覆盖 |

### 2.1.2 为什么以内部质量为主

外部质量（如功能正确性、响应时间）的评估需要**完整可运行的部署环境**：MySQL 数据库、Redis 缓存、Elasticsearch 检索服务、第三方 OAuth 平台的真实 AppKey。本次泛读阶段不具备这些条件，因此：

- **外部质量只做"静态可推断"的部分**：通过读代码判断异常是否被正确处理、并发写是否安全、查询是否存在 N+1，这些不需要真的把服务跑起来；
- **内部质量做完整分析**：静态分析工具只需要源码文本，不依赖运行环境，可以全量、可复现地执行。

这个取舍在报告中明确说明，避免"声称做了没做的事"。

## 2.2 软件质量分析方法

本次采用**四种方法交叉验证**，不同方法回答不同问题：

| 方法 | 回答什么问题 | 适用质量要素 | 局限 |
|---|---|---|---|
| ① 人工代码阅读 | 设计是否合理？业务规则是否正确？ | 设计质量、正确性 | 主观、不可量化、覆盖不全 |
| ② 静态代码分析 | 规范符合度、复杂度、注释量如何？ | 可读性、可维护性、规范性 | 不理解业务语义，会误报 |
| ③ 安全专项扫描 | 有没有可利用的漏洞？ | 安全性 | 只查已知模式，漏报逻辑漏洞 |
| ④ 单元测试执行 | 改动有没有破坏原有行为？ | 功能正确性 | 需要可运行环境 |

### 2.2.1 人工代码阅读

**做法**：按模块分工（每人负责 1～2 个应用），逐文件通读，重点看四类地方：

1. **业务规则的实现**：例如评论开关如何判定、OAuth 绑定在什么条件下发生；
2. **异常与边界**：空值、重复数据、并发写如何处理；
3. **设计意图**：为什么这个类要抽象、那个包要独立；
4. **可疑之处**：写完注释后仍然"讲不通"的地方——这往往就是缺陷所在。

**产出**：每模块一份《注释与质量分析》，其中"发现的质量问题"一节必须给出**文件:行号 + 现象 + 影响 + 建议**。

**为什么必须有这一步**：静态工具查不出逻辑缺陷。例如本项目 `oauth` 模块中"补邮箱页从隐藏域取 `oauthid`，可被篡改为任意用户 id"这一越权问题，所有工具都报告为"通过"——因为代码在语法、风格、复杂度上都合规，问题出在**业务逻辑的信任边界**上。这类问题只能靠人读出来。

### 2.2.2 静态代码分析

**做法**：用工具对全量源码做机器扫描，得到可复现的量化指标。本次关注的指标分四组：

| 指标组 | 具体指标 | 判定标准 |
|---|---|---|
| 注释 | docstring 覆盖率、注释行占比、前缀注释合规率 | 覆盖率 ≥ 80% 为合格 |
| 复杂度 | 圈复杂度 CC、可维护性指数 MI、函数长度 | CC ≤ 10 为良好，>20 为需重构 |
| 规范 | PEP 8 违规数、D1xx 文档字符串缺失数 | 新增代码零新增违规 |
| 冗余 | 未使用变量/导入、死代码 | 尽量为 0 |

**统计口径必须固定**，否则不同人跑出的数字无法比较。本组约定的两个核心口径是：

- **口径 A（docstring 覆盖率）** = 已写 docstring 的节点数 ÷ 应写节点数 × 100%，节点包含"模块 + 每个类 + 每个函数/方法"；
- **口径 B（注释行占比）** = （整行注释 + 行尾注释 + 文档字符串行）÷ 总行数 × 100%。

> 口径 B 与 radon 自带的 `(C + M % L)` 存在 0～5 个百分点的差异：radon 把**单行 docstring** 归入 `Single comments` 而非 `Multi`，导致 `(C+M)` 漏统计它。本组以自建脚本为准，并附 radon 原始输出做交叉验证。这个差异已写入《注释扫描工具命令手册》第 3.2 节。

### 2.2.3 安全专项扫描

**做法**：用 `bandit` 做模式匹配式扫描，重点看五类风险：

1. 硬编码口令/密钥（`B105`/`B106`/`B107`）；
2. 命令注入（`B605`/`B602`）；
3. 弱加密算法（`B303`/`B324`）；
4. 不安全的反序列化、`eval`/`exec`；
5. 关闭证书校验、绑定 `0.0.0.0` 等部署风险。

**局限**：bandit 只认"已知危险模式"，查不出**授权逻辑错误**（如越权访问）。因此它只能作为补充，不能替代人工阅读。

### 2.2.4 单元测试执行

**做法**：运行项目自带的测试套件，确认两点：

1. **基线是否通过**：如果接手时测试就是红的，说明存在既有缺陷，需要单独记录；
2. **改动是否破坏行为**：本次任务要求"只补注释、不改逻辑"，因此补注释前后各跑一次，两次结果必须完全一致。

**本次实际做法**：项目 `settings.py` 把数据库写死为 MySQL，而本机未安装 MySQL 服务。为在不修改原配置的前提下运行测试，额外建立一个**仅用于测试的配置覆盖文件**，把数据库换成内存 SQLite：

```python
# djangoblog/test_settings_sjq.py
from djangoblog.settings import *  # noqa

DATABASES = {
    'default': {'ENGINE': 'django.db.backends.sqlite3', 'NAME': ':memory:'}
}
```

然后以 `DJANGO_SETTINGS_MODULE=djangoblog.test_settings_sjq` 运行。这样既不污染生产配置，也能验证逻辑。

### 2.2.5 四种方法的关系

四种方法不是并列的，而是**层层收敛**：

```
人工阅读  ──发现"讲不通的地方"──>  提出怀疑
    │                                │
    ▼                                ▼
静态分析  ──量化"有多严重"──>  排序优先级
    │
    ▼
安全扫描  ──确认"是否可利用"──>  判定风险等级
    │
    ▼
单元测试  ──验证"改动是否安全"──>  给出修复信心
```

举例说明这个链条怎么用：人工阅读发现 `oauth/views.py` 的 `authorize()` 函数"太长、看着费劲"（怀疑）→ 用 radon 测出 CC=17，是全模块唯一 C 级块（量化）→ bandit 报告该文件无高危问题（说明不是安全问题，是可维护性问题）→ 补注释后用 33 个单元测试确认未破坏行为（验证）。这样得出的结论才有依据。

## 2.3 软件质量分析工具

本次共使用 **7 个工具**，全部为开源工具，均可通过 `pip` 安装、可重复执行。工具选择原则是：**每个工具解决一类明确问题，不重复、不堆砌**。

### 2.3.1 工具总览

| 工具 | 版本 | 主要功能 | 支持分析的质量方面 | 本次用途 |
|---|---|---|---|---|
| **interrogate** | 1.7.0 | 统计 docstring 覆盖率 | 可读性、文档完整性 | 口径 A 主指标 |
| **radon** | 6.0.1 | 圈复杂度、可维护性指数、原始行指标 | 可维护性、复杂度 | CC/MI/注释占比 |
| **flake8** | 7.5.0 | PEP 8 规范检查（pycodestyle + pyflakes + mccabe） | 规范性、冗余代码 | 规范符合度 |
| **pydocstyle** | 6.3.0 | 文档字符串规范检查（D1xx 系列） | 可读性 | docstring 质量 |
| **pylint** | 4.1.3 | 综合静态检查（配合 `pylint-django`） | 规范性、可维护性、潜在缺陷 | 综合评分 |
| **bandit** | 1.9.4 | 安全漏洞模式扫描 | 安全性 | 安全专项 |
| **vulture** | 2.16 | 死代码检测（未使用变量/导入/函数） | 可维护性、冗余 | 冗余代码清理 |

### 2.3.2 interrogate：docstring 覆盖率

**功能**：统计"应当有文档字符串的节点"中实际写了多少个，输出覆盖率百分比与逐文件明细。

**统计对象**：模块本身、每个类、每个函数与方法（含 `async`、含嵌套）。

**关键用法**：

```bash
# 排除自动生成的迁移文件（-e 必须用 glob 模式，写 -e migrations 不生效）
interrogate -e "*/migrations/*" src/oauth

# 设置及格线，低于 80% 直接失败（可挂 CI）
interrogate --fail-under 80 -e "*/migrations/*" src/oauth
```

**本项目实测结果**（`src/` 下各模块）：

| 模块 | docstring 覆盖率 |
|---|---:|
| blog | 62.8% |
| comments | 59.8% |
| djangoblog | 59.6% |
| plugins | 56.8% |
| accounts | 54.0% |
| oauth | 29.3% |
| servermanager | 1.6% |
| **全项目** | **53.3%** |

**能说明什么**：全项目超过一半的模块/类/函数没有文档字符串，`servermanager` 几乎为零。这个指标直接对应"新人接手要花多久才能看懂"。

**不能说明什么**：docstring 写了不等于写得好——一个只写"这是一个函数"的 docstring 同样计入覆盖率。因此需要配合 `pydocstyle` 检查质量。

### 2.3.3 radon：复杂度与可维护性

**功能**：三组指标。

| 子命令 | 输出 | 用途 |
|---|---|---|
| `radon cc` | 每个函数/类的圈复杂度（CC）与等级 A~F | 找出"太绕"的函数 |
| `radon mi` | 每个文件的可维护性指数（MI）与等级 A~C | 找出"最难维护"的文件 |
| `radon raw` | LOC/SLOC/LLOC、注释行数、空行数 | 交叉验证注释占比 |

**等级判定标准**：

| 指标 | A | B | C | D | E | F |
|---|---|---|---|---|---|---|
| 圈复杂度 CC | 1–5 | 6–10 | 11–20 | 21–30 | 31–40 | 41+ |
| 可维护性 MI | 20–100 | 10–19 | 0–9 | — | — | — |

**关键用法**：

```bash
radon cc src/oauth -s -a          # -s 显示复杂度，-a 输出平均值
radon cc src/oauth -j             # JSON 输出，便于脚本统计分布
radon mi src/oauth -s             # 可维护性指数
radon raw -s src/oauth            # 原始行指标
```

**本项目实测结果**：

全项目 1040 个函数/类块，复杂度分布如下：

| 等级 | 数量 | 占比 |
|---|---:|---:|
| A（1–5） | 984 | 94.6% |
| B（6–10） | 36 | 3.5% |
| C（11–20） | 15 | 1.4% |
| D（21–30） | 3 | 0.3% |
| E（31–40） | 2 | 0.2% |
| **平均** | **2.18** | — |

最复杂的 6 个块：

| 复杂度 | 位置 | 说明 |
|---:|---|---|
| 38 | `djangoblog/whoosh_cn_backend.py: search` | 全文检索查询构造，213 行、18 个参数 |
| 31 | `djangoblog/whoosh_cn_backend.py: build_query_fragment` | 查询片段拼接 |
| 29 | `djangoblog/whoosh_cn_backend.py: _process_results` | 检索结果处理 |
| 26 | `plugins/image_lazy_loading/plugin.py: _apply_optimizations` | 图片 HTML 批量改写 |
| 24 | `djangoblog/whoosh_cn_backend.py: more_like_this` | 相似文章推荐 |
| 17 | `oauth/views.py: authorize` | 第三方登录回调主流程 |

可维护性指数最低的文件：

| MI | 文件 | 等级 |
|---:|---|---|
| 5.76 | `djangoblog/whoosh_cn_backend.py` | **C（最难维护）** |
| 18.54 | `oauth/oauthmanager.py` | B |
| 32.80 | `servermanager/robot.py` | A |
| 37.93 | `blog/templatetags/blog_tags.py` | A |

**能说明什么**：94.6% 的函数处于 A 级，说明**整体代码不复杂**；但 `whoosh_cn_backend.py` 一个文件贡献了 4 个 D/E 级块，是全项目最大的技术债集中点。

**不能说明什么**：复杂度低不等于代码好——一个 500 行、全是简单语句但毫无注释的文件，CC 也很低。因此必须与注释指标一起看。

### 2.3.4 flake8：PEP 8 规范检查

**功能**：整合三个检查器——`pycodestyle`（编码风格）、`pyflakes`（未使用变量/导入、未定义名字）、`mccabe`（复杂度）。

**关键用法**：

```bash
flake8 --max-line-length=120 --exclude=migrations,__pycache__ --statistics src/
```

**本项目实测结果**：全项目共 **386 条**违规，按类型统计：

| 违规码 | 含义 | 数量 |
|---|---|---:|
| W293 | 空行含空白字符 | 115 |
| F841 | 局部变量赋值但未使用 | 65 |
| F405 | 可能未定义（来自 `import *`） | 63 |
| F401 | 导入但未使用 | 44 |
| F403 | 使用 `from x import *` | 14 |
| E501 | 行超过 120 字符 | 14 |
| W291 | 行尾空白 | 10 |
| E302 | 类/函数前空行不足 | 9 |
| W605 | 无效转义序列 | 8 |
| E722 | 裸 `except:` | 7 |
| W292 | 文件末尾无换行 | 6 |
| E128 | 续行缩进不足 | 6 |
| W391 | 文件末尾多余空行 | 5 |
| E303 | 空行过多 | 5 |
| E127 | 续行缩进过多 | 4 |
| E305 | 定义后空行不足 | 3 |
| 其他（各 1～2 条） | E203/E265/E402/E741/E129/F541/F824 | 8 |
| **合计** | — | **386** |

**能说明什么**：`F405 + F403` 合计 77 条，直指同一个根因——`djangoblog/admin_site.py` 等文件使用了 14 处 `from x import *`。这类问题会掩盖真实的命名冲突，是"看起来能跑、改起来出事"的典型来源。

**不能说明什么**：flake8 默认不检查行长度（需显式 `--max-line-length`），也不检查文档字符串。所以它查出的问题数是**下限**，不是全部。

### 2.3.5 pydocstyle：文档字符串规范

**功能**：按 PEP 257 检查 docstring 的"写法是否规范"，与 interrogate 的"有没有写"互补。

**检查项分类**：

| 编号 | 含义 |
|---|---|
| D100 | 模块缺 docstring |
| D101 | 类缺 docstring |
| D102 | 公共方法缺 docstring |
| D103 | 公共函数缺 docstring |
| D104 | 包缺 docstring |
| D105/D106/D107 | 魔术方法/`__init__` 缺 docstring |
| D205/D400 | 摘要行格式不规范（首行未空行、未以句号结尾） |

**本项目实测结果**：全项目共 **907 条**，其中 D1xx（缺 docstring）类 **571 条**，D4xx（格式）类 232 条。

分模块的 D1xx 数量：

| 模块 | D1xx 数量 |
|---|---:|
| blog | 149 |
| djangoblog | 109 |
| oauth | 106 |
| servermanager | 66 |
| accounts | 62 |
| comments | 46 |
| plugins | 31 |
| 根目录（manage.py 等） | 1 |

**需要特别说明的误报**：本项目 docstring 大量使用中文，以"。"结尾，而 `pydocstyle` 只认英文句号"."，因此产生了 **225 条 D400 误报**。这属于**工具对中文的不适配**，不是代码缺陷。报告中保留说明，但不据此扣分——这也是"不能迷信工具"的具体例子。

### 2.3.6 pylint（+ pylint-django）：综合检查

**功能**：覆盖最广的 Python 静态检查器，检查项分为六类：约定（C）、重构建议（R）、警告（W）、错误（E）、致命（F）、信息（I）。配合 `pylint-django` 插件可理解 Django 的模型、视图、管理器等特殊结构，避免大量误报。

**关键用法**：

```bash
# 必须指定 settings 模块，否则 Django 相关检查会误报
DJANGO_SETTINGS_MODULE=djangoblog.settings \
pylint --load-plugins=pylint_django \
       --django-settings-module=djangoblog.settings \
       --disable=C,R --recursive=y --ignore=migrations,__pycache__ src/
```

**本项目实测结果**：综合评分 **9.35/10**，共 468 条提示（警告 465 条、错误 3 条）。按类型 Top 10：

| 类型 | 数量 | 含义 |
|---|---:|---|
| `unused-variable` | 70 | 变量赋值后未使用 |
| `logging-fstring-interpolation` | 70 | 日志用 f-string，应改用惰性格式化 |
| `unused-argument` | 48 | 参数未使用（含 Django 信号回调的固定签名） |
| `broad-exception-caught` | 43 | 捕获过于宽泛的 `Exception` |
| `unused-import` | 39 | 导入未使用 |
| `redefined-outer-name` | 21 | 内层作用域覆盖外层同名变量 |
| `redundant-u-string-prefix` | 20 | Python 3 中多余的 `u''` 前缀 |
| `attribute-defined-outside-init` | 17 | 属性在 `__init__` 外定义 |
| `wildcard-import` | 15 | 通配符导入 |
| `redefined-builtin` | 13 | 覆盖内置名 |

3 条错误级（E）问题：

| 编号 | 位置 | 问题 |
|---|---|---|
| E1101 | `blog/models.py:45` | `BaseModel` 实例访问不存在的 `views` 成员（抽象基类未声明该字段） |
| E1101 | `djangoblog/utils.py:115` | `Markdown` 实例访问不存在的 `toc` 成员 |
| E1205 | `djangoblog/blog_signals.py:91` | 日志格式串参数个数不匹配（运行时可能报错） |

**能说明什么**：9.35 分说明**整体规范度较高**；但 3 条 E 级问题中，`E1205` 是真实的运行时隐患（日志格式化参数不匹配会在打日志时抛异常），值得优先修复。

**不能说明什么**：pylint 分数**受配置影响极大**。本次禁用了 C（约定）和 R（重构）两类，只保留 W/E，否则分数会明显偏低。报告中必须写明配置，否则分数不可比。

### 2.3.7 bandit：安全扫描

**功能**：基于 AST 的 Python 安全漏洞模式扫描，把问题分为 HIGH/MEDIUM/LOW 三级严重度与置信度。

**关键用法**：

```bash
bandit -r src/ -x migrations,__pycache__ -f json -q
```

**本项目实测结果**：共 **220 条**，其中 HIGH 2 条、MEDIUM 54 条、LOW 164 条。按类型：

| 检测项 | 数量 | 含义 |
|---|---:|---|
| B106 | 118 | 函数调用中硬编码口令 |
| B105 | 24 | 字符串中硬编码口令 |
| B308 | 24 | `mark_safe` 使用（XSS 风险） |
| B703 | 23 | Django `mark_safe`（模板注入风险） |
| B101 | 9 | 使用 `assert`（`-O` 优化时会被移除） |
| B110 | 7 | `try/except/pass` 静默吞异常 |
| B113 | 6 | `requests` 调用未设超时 |
| B107 | 4 | 函数默认参数中硬编码口令 |

**2 条 HIGH 级问题**：

| 位置 | 检测项 | 问题 |
|---|---|---|
| `plugins/image_lazy_loading/plugin.py:141` | B324 | 使用 MD5 弱哈希 |
| `servermanager/api/commonapi.py:49` | B605 | 以 shell 方式启动子进程，存在命令注入风险 |

**能说明什么**：B106 的 118 条集中在测试代码（`create_user(password='...')` 这类测试数据），属于**误报集中区**；但 B605（命令注入）与 B324（弱哈希）是真实需要关注的点。

**不能说明什么**：bandit **查不出越权**。本项目 `oauth` 模块存在"可篡改隐藏域 `oauthid` 改写他人邮箱"的水平越权问题，bandit 对 `oauth` 目录报告 0 条 HIGH 级问题——因为该代码在语法层面完全"正常"。这正是需要人工分析补位的地方。

### 2.3.8 vulture：死代码检测

**功能**：找出未被引用的变量、导入、函数、类与不可达代码，按置信度（60%～100%）输出。

**关键用法**：

```bash
vulture src/ --exclude=migrations,__pycache__ --min-confidence 80
```

**本项目实测结果**：置信度 ≥80% 的死代码共 **32 条**，其中未使用变量 20 条、未使用导入 12 条。典型例子：

| 位置 | 类型 | 内容 |
|---|---|---|
| `blog/views.py:23` | 未使用导入 | `ArticleListMixin` |
| `blog/views.py:399` | 未使用导入 | `page_not_found_view` 等 3 个错误视图 |
| `djangoblog/elasticsearch_backend.py:187` | 未使用变量 | `preferred_query` |
| `blog/admin.py:42` | 未使用变量 | `modeladmin` |

**能说明什么**：死代码不会导致错误，但会误导阅读者（"这个导入是干什么的？"）并增加维护负担。清理成本低、收益明确，适合作为第一步改进。

**不能说明什么**：vulture 会误报**被框架通过字符串反射调用的代码**。例如 Django 的信号接收函数、模板标签、管理命令的 `handle()`，在静态分析看来都"没人调用"。因此不能无脑删除，必须逐条确认。

### 2.3.9 工具组合的取舍说明

**为什么不用 SonarQube / CodeClimate 等平台工具**：这类工具功能更强，但需要部署服务、配置数据库、且多数商业版收费。本次为课程作业，7 个 CLI 工具已能覆盖全部需要的维度，且**可复现、可脚本化**——任何人 clone 仓库、按《注释扫描工具命令手册》装好环境，就能跑出完全相同的数字。这比"截图某个平台的结果"更有说服力。

**工具之间如何互补**：

| 想回答的问题 | 用哪个工具 | 为什么不用其他 |
|---|---|---|
| 注释写没写 | interrogate | flake8/pylint 不单独统计 docstring 覆盖率 |
| 注释写得好不好 | pydocstyle | interrogate 只查有无，不查格式 |
| 函数是否太复杂 | radon cc | pylint 的复杂度检查粒度粗、不输出具体数值 |
| 文件是否难维护 | radon mi | 其他工具无此指标 |
| 有没有规范违规 | flake8 | pylint 更全但更慢、误报更多 |
| 综合评分 | pylint | flake8 不输出评分 |
| 有没有安全漏洞 | bandit | pylint 的安全检查覆盖远不如 bandit |
| 有没有死代码 | vulture | flake8 的 F401 只查导入，不查未使用函数/变量 |

**必须强调的一点**：7 个工具**全部报告通过**的代码，仍然可能存在严重缺陷。本项目 `oauth` 模块就是例子——interrogate 在补注释后给出 100%，radon 给出 A 级，flake8 无新增违规，但人工阅读发现 8 个质量问题（含 1 个越权、2 个未捕获异常导致的 500）。**工具负责"排除低级问题"，人工负责"发现逻辑问题"，二者不可互相替代**。

## 2.4 本章小结

本章确定的"要素—方法—工具"框架如下：

1. **质量要素**：以内部质量为主（可读性、可维护性、可测试性、安全性、规范性、设计质量），外部质量只做静态可推断部分（缺陷密度、性能、可靠性）。
2. **分析方法**：人工阅读 + 静态分析 + 安全扫描 + 单元测试，四者层层收敛，人工负责发现、工具负责量化、测试负责验证。
3. **分析工具**：7 个开源 CLI 工具（interrogate、radon、flake8、pydocstyle、pylint、bandit、vulture），各自解决一类明确问题，全部可复现。
4. **统计口径**：固定口径 A（docstring 覆盖率）与口径 B（注释行占比），并说明与 radon 原始口径的差异来源，保证六人数据可比。
